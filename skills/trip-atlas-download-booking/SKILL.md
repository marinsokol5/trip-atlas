---
name: trip-atlas-download-booking
description: Save a reservation (stay, flight, train, bus, transfer, activity) as one clean PDF beside a Trip Atlas itinerary, named consistently and linked from its booking. Use when the user wants a booking, ticket, voucher or confirmation email downloaded, printed, turned into a PDF or added to the trip.
---

**Read only.** On booking sites and inboxes only navigate and read: never click pay, cancel, change, message, review or save. The user logs in themselves; never type, ask for or store passwords.

1. **Read the reservation** from the page, email or file the user points to, in whichever browser they are logged into: name (plus the original-script name), address, GPS, start and end with local times, travellers, confirmation code/PIN, price, payment status and date, cancellation deadline, contact phone, and what is included (meals, baggage, pickup). Read the provider's messages too; they hold the real must-knows (arrival cutoff, cash only, meeting point).
2. **Fill gaps from the property's or operator's own page** (GPS, check-in window, rules). Where sources disagree, keep what was confirmed to the user and tell them.
3. **Keep the official document when it is good**: one or two pages holding the facts above, as with most Booking.com confirmations, airline e-tickets and rail tickets. Ask the user to click its download/print button (embedded browsers often block the print dialog) and say where it landed; if that is impossible, print the page with its own print stylesheet.
4. **Otherwise build one page** from [template.html](template.html) (Airbnb, email-only bookings, transfers, activity vouchers): keep only the rows that apply, translate rules to short English, no provider branding. Render with headless Chrome: `chrome --headless=new --no-pdf-header-footer --print-to-pdf=out.pdf file:///path/page.html`, then open the PDF and check it is one page and every value matches the source. Merge several travellers' tickets into one PDF, the user's first.
5. **Save** beside the itinerary as `documents/<country>/YYYY-MM-DD-<place>-<what>.pdf`, so files sort by date: `YYYY-MM-DD` is the check-in, departure or activity date; `<country>` is the trip country it belongs to in lowercase English (a flight to or from home goes under the trip country at the other end); `<place>` and `<what>` are lowercase ASCII kebab-case, e.g. `2027-05-12-kyoto-ryokan-hanaya.pdf`, `2027-05-11-amsterdam-tokyo-flight.pdf`, `2027-05-15-kyoto-tokyo-train.pdf`. Move a replaced file to the trash or scratchpad, never delete it. Keep no full-page captures (`.mhtml`, inbox screenshots); they carry unrelated private data.
6. **Link it** with the trip-atlas-update-itinerary skill: create or update the booking from the confirmation, add `documents: [{ "label": "Confirmation", "path": "documents/…" }]` (`Ticket` or `Voucher` where fitting), put step 1's must-knows in its `notes` (`important` when missing it costs money or the booking), then run `npx trip-atlas check <itinerary>`. Finally tell the user the must-knows and any mismatch you found.
